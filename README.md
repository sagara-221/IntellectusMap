# 理解の地図 — AI学習診断 PoC

テーマを知識へ分解し、各項目の自己評価と必要な確認問題から理解度の目安を示す検証用アプリです。画面では理解度を「高・中・低・未判定」で表示し、計算用の数値は内部に保持します。知識グラフで関心のある枝を「さらに分解」できます。開始時には任意の「テーマの詳細情報」を指定できます。確認問題の形式は4択と正誤判断に固定しています。

- Backend: Python 3.12 / FastAPI / Pydantic / Google Cloud Firestore (Local: SQLite/Firestore)
- Frontend: React / TypeScript / Vite / React Flow
- Gemini: REST Adapter、構造化出力、Pydantic検証、Timeout、Retry
- 任意のテーマを入力して診断を開始できます。固定教材・デモプロバイダーは自動テスト（pytest）の互換性用として維持されています。

診断ロジックの動作と、LLMの教育的な診断品質は別々に検証します。提供されたサービスアカウントJSONによるVertex AI実APIの一回答フローは検証済みです。診断精度の検証は別途必要です。

## 起動

操作方法は [IntellectusMap マニュアル一覧](output/pdf/README.md) を参照してください。アイコン付きの簡易版・詳細版・動作ロジック解説を、PDFとHTMLで掲載しています。

プロジェクトのルートで実行します。

```bash
python3 -m venv .venv
.venv/bin/pip install -r backend/requirements.lock
npm --prefix frontend ci
test -f .env || cp .env.example .env
```

ターミナル1:

```bash
.venv/bin/uvicorn app.main:app --app-dir backend --host 127.0.0.1 --port 8000 --reload
```

ターミナル2:

```bash
npm --prefix frontend run dev
```

- 画面: http://localhost:5173
- APIドキュメント: http://127.0.0.1:8000/docs
- ヘルスチェック: http://127.0.0.1:8000/api/health

地図と調査手帳を使う画面が `/` です。従来の画面は `/legacy.html` に残しており、画面右上から切り替えられます。既存の `/atlas.html` も地図画面として利用できます。両画面は同じ認証・セッション・バックエンドAPIを利用します。追加の技術仕様は [地図UI向けバックエンド仕様](doc/地図UI向けバックエンド仕様.md) を参照してください。

画面から学びたい任意のテーマ（例：機械学習、コンピュータネットワーク、統計学など）を入力して診断を開始してください。

「テーマの詳細情報」には、テーマの背景、章・項目、到達目標、対象学年や前提レベル、範囲外にしたい内容を入力できます。Geminiモードでは、初回の主要項目分解、選択後の追加分解、確認問題の生成に同じ指定を渡します。学年やレベルの指定から「この基礎項目は理解済み」とは推定せず、テーマに関係する基礎知識まで不足箇所を探せます。明示的に除外した内容は範囲外として扱います。入力内容はセッションと診断記録に保存されます。

## 問題の順序（既存の自動探索セッション）

1つの項目（Concept）の診断を終えてから次の項目へ進みます。特定の項目の確認が続いている間は、その項目の問題を続けて出します。項目内では確認する能力（Target）を分散させます。

問題数は最初に固定せず、各回答後に判定します。理解済みなら次の項目へ、弱点が明確なら深掘りや分析結果の確認へ進みます。7問でも判断できない場合は不確実としてその項目の反復を終えます。深掘り後の子項目も同様に1項目ずつ確認します。

## 探索の終了と継続（既存の自動探索セッション）

全体の20問上限を撤廃しました。テーマを第1層と数え、第3層以降から次の層へ進む前に分析結果を提示します。

- **分からない箇所が分かった**: 集中探索では診断を終了します。全網羅ではその項目だけを終えて、残りの項目の探索を続けます。理解度・習得状態は変更しません。
- **まだ分からない · 次の層へ進む**: 分解候補を展開します。さらに深掘りする際も同じ確認を行います。

判断待ちの間は生成を止めます。結果と選択を保存し、リロードや通信障害後も再開できます。これ以上分解できなければその旨を伝え、残りの項目を探索します。候補が尽きた場合の「原因未特定」と、ユーザーが納得した終了は区別します。

全体の問題数・深度にデフォルト上限はありません。単一項目への反復は7問までとし、不確実なままなら別の項目または分析結果の確認へ進みます。変更前の未完了セッションも新しい設定に移行します。完了済みの記録は保持します。デモ教材にも固定の層数上限はありません。固定テンプレートによる分解を、選択した項目について継続します。既存セッションで分解候補が空だったデモ項目も探索できます。100%確認後の表示用分解は、出題を伴わず1段だけ追加します。

## Gemini設定（GCP / Vertex AI）

`gcp_config/` にサービスアカウントのJSON鍵を1つ配置します。今回指定されたファイル形式（`type: service_account`、`project_id`、`private_key`、`client_email`など）に対応しています。プロジェクトIDはJSONの `project_id` を自動使用します。

ルートの `.env` を設定し、バックエンドを再起動してください。今回の環境では作成・設定済みです。

```dotenv
GEMINI_BACKEND=vertex
GEMINI_MODEL=gemini-3.5-flash-lite
GOOGLE_CLOUD_LOCATION=global
```

画面から新しいテーマを開始するとGeminiへ接続します。デモモードは既存セッションとテストの互換性のためにAPIで利用できます。モデル名はコード内に固定せず、利用可能なモデルIDへ `.env` で変更できます。

追加の設定:

```dotenv
# JSONのproject_idと異なるプロジェクトで推論する場合のみ指定
GOOGLE_CLOUD_PROJECT=your-project-id
# 複数の鍵がある場合や別の場所に置く場合のみ指定
GOOGLE_APPLICATION_CREDENTIALS=gcp_config/your-service-account.json
# リージョン固定が必要な場合（モデルの対応リージョンを確認）
GOOGLE_CLOUD_LOCATION=asia-northeast1
```

鍵を自動検出するのは `gcp_config/` 直下のJSONが1つの場合だけです。複数の場合は勝手に選ばず明示指定を求めます。相対パスはカレントディレクトリによらずプロジェクトルート基準です。

認証には `google-auth` を使用し、サービスアカウント鍵からOAuthアクセストークンを取得・更新します。トークンはサーバーのメモリにのみ保持します。Vertex AIの `generateContent` を呼び、APIキーは不要です。テーマ・回答はGoogle Cloudの選択プロジェクトへ送信され、API利用料が発生します。鍵とトークンはブラウザへ返しません。

`gcp_config/` は `.gitignore` / `.dockerignore` で除外します。Dockerでは鍵をイメージに含めず、読み取り専用でマウントします。外部フォルダの鍵を使う場合はComposeのマウント元も変更してください。コンテナ内で複数JSONから選ぶ場合は `GCP_CREDENTIALS_CONTAINER_PATH=/run/gcp_config/your-service-account.json` を指定できます。

- `/api/health` の `gemini_ready` は設定が揃っていることを示します。API権限・課金・モデル利用可否の疎通確認とは別です。
- 403: Vertex AI APIの有効化、課金設定、サービスアカウントのVertex AI利用権限（例：Vertex AI User）を確認してください。
- 404: モデル名・リージョン・対象プロジェクトでの利用可否を確認してください。
- 429: 利用上限のため、時間をおいて再試行してください。

[Vertex AIの公式クイックスタート](https://docs.cloud.google.com/vertex-ai/generative-ai/docs/start/quickstart)に沿って、`global` は `aiplatform.googleapis.com`、リージョン指定時は `{region}-aiplatform.googleapis.com` を使用します。[GenerationConfig](https://cloud.google.com/vertex-ai/generative-ai/docs/reference/rest/v1beta1/GenerationConfig)の `responseMimeType` / `responseJsonSchema` で構造化出力を指定します。

Vertex AIにはデコード制約の複雑さに上限があるため、送信するスキーマから説明文・既定値・配列長などの制約を省略します。返答は元のPydanticモデルで検証し、件数・型・ID整合性などの制約は維持します。

従来のDeveloper APIが必要な場合のみ `GEMINI_BACKEND=developer` と `GEMINI_API_KEY` を明示設定してください。認証失敗時に別の接続先へ自動切り替えすることはありません。

## セッション・記録

本番環境（Cloud Run）では Google Cloud Firestore（Native モード）にセッションや知識マップデータを永続化します。ローカル開発環境では設定（`DATABASE_BACKEND`）に応じて Firestore または SQLite を自動選択します。同じタブの再読み込みでは最後に開いたマップを復元します。旧セッションから発散して新しいマップを作るときは、その元セッションをマップ系統へ登録します。

各Conceptの「知識を広げる」を押すと繋がりMAPへすぐ移動し、既定で5件の発散候補を生成します。生成中は繋がりMAPに進行表示を出し、完了すると「今回の候補」として強調し、系統の元テーマを中央に置いて、新しい候補を含む全体が見えるよう表示を合わせます。関連するマップや候補は元テーマから放射状に広がり、派生したマップからさらに広げた候補は、その枝の外側に配置します。候補を選ぶと関係・理由を確認し、そのまま深掘りを始められます。生成中にタブを移動しても処理を続け、戻ったときは再生成しません。生成失敗は繋がりMAPから再試行できます。候補はすべて保存し、「繋がりMAP」に未探索のノードと点線で表示します。再度「知識を広げる」や「別の候補を探す」を選ぶと、そのマップから過去に生成した候補の名前・関係・理由と作成済みのテーマをAIへ渡し、未提案の内容を生成します。同名・表記違いの候補は検証で除外し、同じマップからの同時生成は順に処理して直前に保存した候補も除外します。候補の詳細を見ただけではマップを作らず、「このテーマで深掘りを始める」を押したときに独立したマップを生成します。新しいマップには発散元のMap・Concept・関係・理由と同じ系統IDを保存します。「深掘りマップ一覧」画面では系統の区切りを設けず全マップを一覧表示し、マップ名・テーマの詳細情報の検索、更新順・名前順・理解度確認数・理解度「低」の項目数による並び替え、理解度確認済み・理解度「低」があるマップの絞り込みができます。編集、削除、回答履歴の確認もできます。「繋がりMAP」では発散によるMAP間の関係をグラフで表示し、選択したMAPの発散元、関係の理由、理解状態を確認できます。未探索の候補から「このテーマで深掘りを始める」を選ぶと独立したマップを生成し、その候補ノードを作成済みのマップとして表示します。「知識ノード一覧」では全マップの判定済み項目を検索・理解度や対象マップで絞り込み・並び替えできます。両一覧の検索・並び順・絞り込みは共通の操作欄にまとめ、表示件数と指定中の条件を表示します。条件は個別に解除するか、「条件をクリア」で初期表示に戻せます。未判定の項目は一覧と件数から除外します。同一と判定済みのConceptは1行にまとめ、マップごとの理解度、信頼度、自己評価、問題の回答履歴を詳細で確認できます。マップ間で理解度が異なる場合は「マップで差あり」と示します。履歴には回答元のマップも表示します。マップを削除しても、他のマップに参照されるCanonical Conceptは残ります。

別のマップのConceptとEmbedding検索・既存の統合判定で `same` と確認された場合のみ、回答根拠と自己評価を共有します。判定が異なる、または統合処理が失敗した場合は独立したConceptとして扱います。マップ横断の照合は生成後にバックグラウンドで行い、完了時に画面の理解状態を更新します。保存済みEmbeddingは全件検索し、未索引の旧Conceptは設定件数だけ追加計算するため、旧Conceptのすべてが初回から照合されるわけではありません。

「記録を保存」で、回答済み問題、Evidence、Target状態、判定理由、診断ポリシー履歴、回答負荷の指標をJSON出力できます。回答前の正答はAPIレスポンスにも含めません。正答を含む全セッション情報はFirestore（またはローカルDB）内に保存されます。

「新しい会話」で、深掘りマップ・理解度・会話からの根拠を残したまま会話の文脈を切り替えられます。「会話履歴」から過去の会話を確認でき、過去の会話は閲覧のみです。最新の会話へ戻って続けられます。新しい会話では、その会話の発言・整理済みの経験だけを返答生成に渡し、マップの理解状態は引き継ぎます。前の会話の反映待ちジョブと根拠キューは継続し、新しいノードの判定には過去の会話の根拠も使います。遅れて完了した旧ジョブは新しい会話の話題や指示を上書きしません。返答を生成中の間だけ新しい会話の開始を待ちます。旧記録は発言IDを変更せず最初の会話として読み込み、既存の引用と互換性を保ちます。

深掘り画面の「会話で確認」は、経験・考え・困りごとを自由に話し、裏で複数の知識項目へ反映する入口です。会話担当は原文、保存済みの根拠、整理済みの経験、解析中の話題を読み、返答をSSEで逐次表示します。抽出・判定・ノード生成の完了を待ちません。相談への回答や内容の整理を中心にし、毎回質問を返す進行やノードごとの口頭試験を避ける汎用の日本語プロンプトにしています。[Gemini公式のプロンプト設計ガイド](https://ai.google.dev/gemini-api/docs/prompting-strategies)、[構造化出力](https://ai.google.dev/gemini-api/docs/structured-output)、[長文処理](https://ai.google.dev/gemini-api/docs/long-context)を確認して設計しました。

最大10万文字の入力を見出し・段落の境界で分割し、原文の引用を持つ経験・説明・不足・用語の言及を抽出します。見出しを引き継ぎ、テーマと関連する複数の枝へ対応づけます。既存の子・準備済みの子を参照して分解や追加を提案し、別の構造確認で親との関係・粒度・重複を検証します。経験のある枝は、理解度をまだ判定できなくても分解対象にできます。複数の分解結果を並列で準備し、最新のグラフに対する反映は順番に行います。新しいノードには過去の関連発言からも判定を行い、根拠がなければ未判定にします。固定の深さ上限はありませんが、一度の更新で開く枝と追加件数には設定上限があり、超えた候補はキューに保持して後続の更新で続行します。さらに先の層まで際限なく生成せず、次の1層を準備します。

抽出した情報は原文の引用とともに永続化した照合キューへ登録します。既存ノードに根拠を反映できた情報は処理済みとして実行待ちから外し、引用・対応履歴は残します。対応先がない情報、粗い親にしか対応できない情報は生成結果との再照合を待ちます。対応する能力はあるが判断材料が不足している情報は「根拠不足」として保留し、それだけを理由に新規ノードを増やしません。

通常の「さらに分解」、初期生成、チャットによる項目の追加で保存された新しいノードも、追加のチャット送信なしで会話履歴から評価します。各枝の保存後に照合し直し、分解・先読みが落ち着いた時点で残る情報から不足項目を提案します。配置確認を通過した候補だけを追加し、生成中にマップが変われば計画を再検討します。未配置の情報は保留し、同じマップへの再照合を繰り返してAPIを使い続けないよう、グラフと準備済み候補の状態を記録します。照合から再帰的な分解は開始しません。新規追加は1回の処理での件数を制限し、残りの候補はキューで続行します。

会話担当には各主要分野の会話根拠・自己評価・問題回答による確認数と深掘り状況から、探索が浅い分野の候補を渡します。ユーザーの質問・相談・話題変更を優先し、関連が自然な場合だけ一つの任意の話題を短く添えます。知識の説明を順に求めたり、回答を必須にしたりせず、自由な経験や考えから裏で理解度を整理します。

理解度の根拠は自己評価・問題回答とは別に保存します。本人が取り組んだ実務・実装・学習の申告は、その作業に直接関係する能力について低い信頼度の暫定評価として扱います。経験の申告だけで高い理解度を確定しないよう、バックエンドでも、具体的な不足を含まない経験の申告はスコア0.5〜0.6の「中」、信頼度0.25以下として扱います。部分的に理解している発言は「中」、明確な理解不足や誤解は「低」として、理解の程度と根拠の確かさを分けて判定します。チャットから作成した項目に具体的な判定がない間は、スコア0.5の「中・暫定」を表示し、信頼度は低いままにします。過去に保存した作成時の暫定値も、表示・集計時に同じ基準で扱います。用語を挙げただけの情報は理解度の根拠にしません。原文の引用とノード・Targetの参照を検証し、AIの説明や抜粋をつなぎ合わせた架空の引用は拒否します。同じ発言の再判定は信頼度を増やさず、新しい発言と問題根拠を能力ごとに集計します。矛盾する根拠の信頼度を下げ、下位項目による親の集計を優先します。

会話から構造の更新が承認された枝は、理解度の確定とは独立して表示します。自己評価の回答は代筆しません。画面には文章の整理・対応づけ・反映・判定の進捗と更新件数を表示し、詳細では引用と判定理由を確認できます。裏の処理中も次の会話を送れます。発言ごとのジョブ、読み取り済みの区切り、承認済みの計画、成功済みの追加をセッションJSONへ保存し、連続送信で古い発言を上書きしません。失敗した更新は「マップへの反映を再試行」、旧形式で保存された未処理の会話は「過去の会話をマップに反映」から開始できます。新しい発言の送信でも未処理・失敗した発言を再開します。

会話履歴とジョブは既存のJSONに保存し、旧記録は空の経験・ジョブとして読み込めます。返答の中断は同じ送信IDで再送でき、マップの反映と独立して復旧します。このPoCのジョブはバックエンド1ワーカーを前提とするプロセス内処理です。再起動で中断したジョブと照合待ちは、マップまたはチャットを開いたときに保存済みの区切り・根拠から再開します。通信などで失敗した処理は画面から再試行できます。`chat.timings` に最初の表示・返答完了・裏の更新の時間を記録します。実モデルでの待ち時間は固定値ではありません。`CHAT_PROCESSING_CONCURRENCY`（標準20）、`CHAT_CHUNK_CHARS`（標準4000）、`CHAT_MAX_EXPANSIONS`（標準10）、`CHAT_MAX_ADDITIONS`（標準10）で並列数・文章の区切り・1回の処理での更新量を調整できます。先読みは既存の `PREFETCH_*` 設定に従います。会話担当に渡す会話本文は `CHAT_HISTORY_MESSAGES`（標準16件）と `CHAT_HISTORY_CHARS`（標準20万文字）の両方で制限します。最新の発言を全文で残し、収まらない古い発言からAI入力の対象外にします。保存した原文やマップ反映用の分割・抽出は省略しません。この文字数の制限に加えて指示文・ノード情報・整理済みの経験もモデル入力に含まれるため、トークン数そのものの上限を保証する設定ではありません。

回答は次の問題の生成前に保存されます。生成失敗時は「問題の生成を再試行」で再開できます。同じ問題・同じ回答の再送はEvidenceを増やしません。並行更新はDBのrevision照合により409で拒否します。

## 知識グラフからの探索（画面の既定）

1. テーマと任意の詳細情報を入力すると、AIが主要項目を生成し、第2層まで自動で分解します。ルートは第0層です。テーマの広さによらず、初期の第2層までの表示に自己評価や会話は必要ありません。
2. 画面には第1層を先に表示します。第2層は標準20並列で裏で準備し、できた枝から自動で表示します。第3層は既定で先読みして保存しますが、さらに先を見たい項目では自己評価後に「さらに分解」を押します。固定の最深層はなく、実際にその項目を分解して有効な子がないと確認した枝で止めます。
3. 知識項目を選ぶと「理解をたしかめる」欄に、その項目の説明・確認する能力と4択の自己評価が表示されます。「理解している／あいまい／分からない／自分では判断できない」から選びます。回答は変更できます。「自分では判断できない」を選ぶと同じ欄で問題を生成して回答し、有効な回答が得られるまで未判定のままです。
4. 上部タブから「深掘りマップ一覧」「繋がりMAP」「知識ノード一覧」へいつでも移動でき、「深掘り」に戻って同じマップを続けられます。自己評価の未回答項目は画面に表示します。問題は選択した項目にだけ生成され、途中で別項目へ移っても未回答問題を保持します。探索内容は操作ごとに保存されます。

知識グラフの「未判定を隠す」を押すと、理解度が判定済みの項目だけを表示できます。テーマのルートは位置の目印として常に残ります。もう一度押すと全項目に戻ります。この切り替えは表示だけを変え、回答や判定結果は変更しません。

親項目とテーマ全体の推定理解度は、直下の全項目に判定があれば、それらの結果を優先して集計します。孫以下の項目が先読み生成されていても、その未回答だけを理由に親を未判定にはしません。直下の項目に未判定が残る場合は、親自身の自己評価や問題結果を暫定的に表示します。親自身にも結果がなければ未判定です。さらに下位の回答がそろうと、各枝の集計結果に更新します。自己評価は自己申告として表示し、問題で確認した結果と区別します。表示上の「高・中・低」は暫定的な目安であり、到達度の百分率や能力の確定値ではありません。

「判定の信頼度」も画面では「高・中・低・未判定」で示します。自己評価だけの内部信頼度は暫定的に0.25（表示は「低」）とし、問題回答がある項目には既存の診断確信度を使います。直下の全項目を集計するときは、その信頼度も平均します。直下に未判定の項目が残る間は親自身の暫定結果と信頼度を表示します。これらの数値は校正された確率ではありません。

診断詳細の回答数は「問題の回答」と「アンケートの回答」を別々に示します。親項目では、その項目自身と配下の項目を合計し、複数の枝から共有される項目は重複して数えません。アンケートの選択肢を変更しても、同じ項目への回答は1件として数えます。



開始APIは第1層を先に返します。第2層は裏で並列生成し、自己評価を待たずに準備できた枝から画面に表示します。遅い枝があっても、他の完成した枝の表示は待たせません。第3層以降の生成済み項目は、親の自己評価または会話による枝の公開まで画面で非表示にします。先読みした次の1層は、利用者が自己評価後に「さらに分解」を押した枝だけ表示します。その操作で新しく表示された子項目について、さらに次の1層を裏で準備します。以降も、利用者が開いた枝の新しい子項目だけを対象にします。生成時に子項目へ付いた末端の推定は確定扱いせず、次の1層の先読みで実際に分解を試します。有効な子がなかった場合だけ停止理由を保存します。分解だけ失敗した場合は、その項目に理由を保存し、同じ操作から再試行できます。深掘りでは対象の説明・評価目標・親からの経路を渡します。正答は回答前のAPIレスポンスに含めません。初期生成・表示層は第2層としてセッションへ保存します。AIが返す初回表示層の値は初回では2、深掘りではnullへ補正し、その値だけを理由に有効な分解計画を拒否しません。旧方式で第1層までだった進行中のマップは、再度開いた際に第2層までの生成を再開し、保存済みの先読みを再利用します。中断した初期生成も読み込み時に再開します。変更前のセッションに保存された目標深さも、分解の制限には使いません。古いセッションの末端判定は維持し、読み込み時に大量の先読みを始めないようにします。

分解を待つ時間を減らすため、バックエンドは初回表示の次の1層を既定で裏で準備します。第3層を非表示で保存します。複数項目を既定で最大20件ずつ並列に生成し、結果をSQLiteへ保存します。先読み中のノードには「生成中」を表示して分解ボタンを無効にし、準備完了後に押せるようにします。先読み失敗時はボタンから再試行できます。利用者が項目を開くと、その操作で新しく表示された子のうち次の分解候補が未準備の項目だけ先読みし、既に準備済みの他の枝は再生成しません。Geminiモードでは表示前の先読みもAPI呼び出しとして課金対象になります。

Geminiによる分解では、先に必要な観点を計画します。計画が具体的な理由付きで停止を決めた場合は、子項目生成を呼ばずにその枝を止めます。分解計画で子が空、または観点との対応が不足した場合だけ、計画を渡して1回修正生成します。それでも整合しなければ観点計画を1回再検討します。子が一度も生成されず再計画も停止と判断した場合だけ枝を止めます。子が生成済みで観点との対応だけが崩れた場合や、再検討後も分解計画なのに子を作れない場合は生成失敗として再試行可能にし、末端とは扱いません。通常は計画と分解の2回のAPI呼び出しで、停止時は計画の1回だけです。不整合時の追加呼び出しは最大3回です。

Geminiモードの分解では、まず必要な観点だけを計画し、その計画を渡して子項目を生成します。生成後は各観点と子の対応を検証し、漏れを含む出力は採用しません。広いテーマの初回分解では、設定上限が6件以上なら少なくとも6つの主要観点・子項目を求めます。概念的な項目が「子なし」と計画された場合は、具体的な適用場面から一度再検討します。通常の分解には計画と生成で2回のGemini API呼び出しが必要で、計画の不足や停止の再検討では追加の呼び出しが発生します。先読み時も同じ回数の呼び出しが発生します。


### 生成・先読みの設定

プロジェクトルートの `.env` で指定します。設定例は [.env.example](.env.example) を参照してください。変更後はバックエンドを再起動します。層数はルートを第0層として数えます。

| --- | ---: | --- |
| `PREFETCH_AHEAD_LAYERS` | `1` | 次の1層を裏で準備する場合は`1`、先読みしない場合は`0`。自動表示する層の生成は続けます。 |
| `PREFETCH_CONCURRENCY` | `20` | 同時に進める先読み項目数。`1`〜`20`。 |
| `INITIAL_MAX_CHILDREN` | `5` | Geminiが初回に作る主要項目の上限。`3`〜`10`。 |
| `EXPANSION_MAX_CHILDREN` | `4` | Geminiが1項目を分解して作る子項目の上限。`2`〜`10`。 |
| `DIVERGENCE_CANDIDATE_COUNT` | `5` | 「知識を広げる」で生成する候補数。`1`〜`15`。 |
| `DIVERGENCE_MAX_CANDIDATE_COUNT` | `15` | 発散候補数の上限。`1`〜`15`。 |
| `CROSS_MAP_MISSING_EMBED_LIMIT` | `10` | Map横断検索時にEmbeddingが未保存の既存Conceptを追加計算する上限。`0`〜`100`。 |
| `CROSS_MAP_CONCURRENCY` | `2` | Map横断の照合を同時に進めるマップ数。`1`〜`10`。 |
| `GEMINI_MODEL` | 省略時 `gemini-3.5-flash-lite` | 利用するGeminiモデルID。 |
| `LLM_TIMEOUT_SECONDS` | `40` | Gemini生成APIの通信タイムアウト（秒）。設定例は`60`。 |

新しい手動探索方式では、初期生成・表示を第2層までに固定します。テーマと詳細情報は項目の内容と分解の観点に反映します。分解の最大層数は設けず、AIが独立した下位項目を作れないと判断した枝で止めます。並列数と先読みの有無はバックエンド再起動後の処理に適用されます。

新しい手動探索方式では、分解の先読み時にConceptのEmbeddingも生成し、同一セッションの保存済みベクトルから類似候補を探します。類似度0.85以上の上位5件だけをGeminiに判定させ、学習上の根拠を共有できる `same` と判定された場合だけCanonical Conceptへ統合します。統合されたノードは1つのまま複数の親へ線を張り、詳細には別名を表示します。Embeddingだけでは統合せず、モデルが失敗した場合も元の分解結果を表示します。先読み後に他の枝が増えた場合は、枝を開く際に現在のグラフと照合してから表示するため、重複ノードを一瞬表示して消すことはありません。ベクトルはセッションJSONと分けてSQLiteに保存します。GeminiモードではEmbedding・判定・Canonical生成もAPI呼び出しとして課金対象です。デモモードの候補検索と判定は固定ロジックです。

チャットからの追加と要素分解の項目が同一と確認された場合、ノードID・回答根拠・配下を保持し、要素分解側の配置へ統一します。チャット由来の仮の親子線を外し、別の関連線として表示しません。親ノードそのものや他の子は削除しません。準備済みの非表示ノードとの統合は、実際の公開時に確定します。統合前は通常の親子関係と共有のpart線を含めて循環を検査し、理解度・信頼度は集計元のノードIDを重複して数えません。統合履歴と変更前の状態を内部に保存し、後続の回答などを失わず復元できる状態に限りサービス内のrestore_mergeで復元できます。同一性・統合内容の成功した判断は入力とプロンプトのハッシュを付けて保存し、変更のない組み合わせへの再呼び出しを避けます。

旧セッションの「項目を選んだときに問題と下位項目を同時生成する」方式は引き続き読み込みます。`manual_flow=combined` として保存された旧方式では、選択時に両方を生成します。新規セッションとAPIリクエストの既定値は `decomposition_first` です。

グラフは丸いノードを線でつなぎ、ドラッグで配置変更、パン・ズーム、検索、選択項目の隣接ノードの強調に対応します。線は親子の構成関係だけを表示します。ノードの色は推定理解度の段階に対応します。新しい手動探索では、第2層までを自動表示し、第3層以降は親の自己評価または会話による枝の公開まで非表示にします。

ノードを追加すると力学シミュレーションを再実行し、既存位置を引き継いで新しい項目の周囲を押し広げます。「配置を整える」では全体を再計算します。

## チャット情報の個別検索と反映

文章の分割・抽出と同時に、知識の粒度（広い領域／個別の知識／具体的な能力）と仮の上位領域を取得します。包含関係を整理する専用のAI呼び出しはありません。広い領域から処理し、具体的な情報の配置には既存・準備済みの枝を優先します。

抽出情報ごとに埋め込み検索し、候補・ルート・親の経路・既存の子・準備済みの子を渡します。候補の重なる、粒度が同じ情報だけを最大3件ずつまとめ、情報IDと引用を分離して判断します。別の情報の候補や引用の流用は検証で拒否します。難しいまとめ処理は個別処理に戻せます。判定には対応づけた情報を引き継ぎ、新しい能力には保存済みの履歴からも検索します。従来の文字一致で40件に絞る方式をマップ判定には使いません。

抽出済みの区切り、情報ごとの対応づけ、ノードと情報ごとの判定を保存します。一部のAPI失敗でも独立した分解・更新を進め、成功結果を保持します。失敗分は保存済みの更新から再試行できます。反映前にノード・能力・つながりを検証し、競合時は最新状態で再処理します。保留情報は生成が落ち着いた後に再照合し、対応先がない場合だけ適切な位置へ追加します。API失敗を直ちに無限再試行せず、新しい情報・グラフ更新・明示的な再試行で再開します。

| 設定 | 標準値 | 意味 |
|---|---|---|
| `CHAT_RETRIEVAL_CANDIDATES` | `12` | 情報1件ごとの検索候補数。 |
| `CHAT_RETRIEVAL_MIN_SIMILARITY` | `0.15` | 候補検索の類似度下限。統合閾値とは別。 |
| `CHAT_ROUTING_BATCH_SIZE` | `3` | 関連情報を対応づけへまとめる最大件数。`1`で個別処理。 |
| `CHAT_ASSESSMENT_BATCH_SIZE` | `3` | 関連情報を理解度判定へまとめる最大件数。`1`で個別処理。 |

プロンプトは日本語で、役割・入力・手順・制約・汎用例を明示します。[Googleのプロンプト設計ガイド](https://ai.google.dev/gemini-api/docs/prompting-strategies)を参考にしています。少数件のまとめ処理の実モデル精度は、同じ抽出情報を個別処理と比較して調整してください。デモ・モック試験は対応関係や根拠の保護を検証するもので、Geminiの意味判断の精度を保証するものではありません。

## 問題形式

新しい知識マップ探索では問題形式を4択と正誤判断の2種類に固定し、内容に応じて使い分けます。設定画面に形式の選択欄はありません。APIで新しい探索を開始する場合も、この2形式以外の指定を拒否します。

追加確認にも同じ形式を適用し、保存・再読み込み後も維持します。旧方式のセッションは保存済みの形式を引き続き使用します。

問題文・選択肢・解説は、段落、リスト、強調、インラインコード、言語名付きコードブロック、LaTeX数式に限定したMarkdownで生成・表示します。HTML、画像、リンクは描画しません。採点用の `expected_answer` はプレーンテキストのまま保持し、表示用の書式と採点値を分離します。

## 回答済み項目の追加確認

グラフで回答済みの項目を選び、診断の根拠にある「追加で確認する」を押すと、新しい問題を1問生成します。評価観点のうち確信度が低いものを優先し、過去の問題文を生成入力に渡して重複を避けます。全回答と根拠を保持し、追加回答を含めて理解度・確信度を再計算します。

習得・弱点の判定済み、通常出題の7問上限到達後、診断終了後も追加確認できます。元の未回答問題・確認待ち・終了状態は保持し、追加確認を回答または中止すると戻ります。手動探索では追加確認への回答後も選択待ちとなり、元の未回答問題は保留して、項目を再選択したときに再表示します。同じ項目に未回答問題がある場合は、その問題を先に回答します。生成失敗は再試行可能で、同一回答の再送でも根拠を二重加算しません。

確信度の計算式は従来どおりで、採点の確かさと評価観点ごとの有効回答数・網羅性から算出します。追加確認だけで必ず上がるわけではなく、既に100%の場合はそれ以上にはなりません。採点不能の回答は確信度を上げる根拠から除きます。これは統計的に校正された確率ではなく、PoCの診断指標です。

## 既存の自動探索記録との互換性

新規画面では自動探索を選択しません。以下は過去の記録・API互換性のために保持している動作です。

- **全項目を網羅**: 各項目の判定を終えてから次の項目へ進み、100%確認済みを除く分解候補を順に探索します。第3層以降で「この項目は分かった」を選ぶと、その枝だけを終了して残りを続けます。
- **最も分かっていない部分を探索**: 同じ層の項目を一通り判定した後、理解度が最も低い分解候補を選びます。同点は確信度の高い項目、さらに同点なら表示順で選択します。理解度を推定できない項目は、数値のある候補より後に扱います。

どちらも、一度正解しただけでは100%確認済みとしません。必要な評価観点と確信度を満たし、全回答が正解だった項目を1段分解してマップに表示します。その子は「親100% · 出題省略」とし、子自身の理解度・確信度・回答根拠は付与しません。子への出題や、さらに下への自動分解は行いません。

全網羅の対象は生成された分解候補です。テーマに含まれる全知識を漏れなく列挙した保証ではありません。探索方式・表示用分解の区別は保存され、再読み込み後も維持されます。既存の記録は集中探索として読み込みます。

手動探索の項目再選択は1問ごとの明示的な追加確認として扱い、習得判定や通常の7問上限を理由に新しい出題を止めません。既存の自動探索セッションの遷移は変更しません。
